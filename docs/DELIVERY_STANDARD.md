# 납품 가능한 제품 개발 기준

이 문서는 조달패스를 ‘화면이 있는 MVP’가 아니라 실제 고객이 돈을 내고 입찰업무에 사용할 수 있는 제품으로 만들기 위한 품질 계약이다.

## 1. 완료의 정의

기능은 코드가 작성되었을 때가 아니라 다음 조건을 모두 만족할 때 완료된다.

- 고객이 실제 공고로 시작해 약속한 결과까지 도달한다.
- 입력, 판단, 출력의 공식 출처를 추적할 수 있다.
- 정상·오류·중단·재개 흐름이 모두 구현되어 있다.
- 자동 테스트와 실제 공고 기반 검증을 통과한다.
- 개인정보·기업정보·결제정보를 안전하게 처리한다.
- 운영자가 오류를 발견하고 복구할 수 있다.
- 고객지원 담당자가 상태를 확인하고 설명할 수 있다.
- 제품 문구가 기능 범위와 한계를 과장하지 않는다.

## 2. 개발 전 필수 산출물

코드를 작성하기 전에 기능마다 다음 문서를 만든다.

1. 고객 상황과 해결해야 할 결과
2. 시작 조건과 완료 조건
3. 전체 사용자 흐름
4. 사용되는 공식 데이터와 갱신주기
5. 판단 규칙과 신뢰도 표시 방식
6. 예외·오류·재시도·취소 흐름
7. 개인정보와 권한 범위
8. 수용 기준
9. 자동 테스트 및 수동 검증 계획
10. 출시·롤백·모니터링 계획

이 항목이 없는 기능은 구현 준비가 되지 않은 것이다.

## 3. 제품 범위

### 첫 판매 버전에 반드시 포함

- 나라장터 공고 URL 또는 공고번호 입력
- 공고 기본정보와 첨부파일 수집
- 회사 프로필 및 보유 자격 입력·저장
- 참가조건을 회사정보와 대조
- 충족·미충족·확인 필요 구분
- 근거 조항과 원문 위치 표시
- 마감 기준 개인화된 할 일 생성
- 필수서류 체크 및 재사용 가능한 회사서류함
- 나라장터 제출 단계 안내
- 제출 완료 증빙과 개찰 결과 추적
- 중단 후 이어하기
- 결제·환불·영수증 또는 세금계산서 흐름
- 운영자용 고객·분석·오류 조회

### 첫 판매 버전에서 제외

- 낙찰을 보장하는 가격예측
- 공동인증서 대리사용
- 사용자의 최종 확인 없는 자동투찰
- 모든 공사·물품·용역 유형 동시 지원
- 낙찰 후 ERP 전체 기능
- 출처 없는 생성형 AI 판단

## 4. 데이터 신뢰성 게이트

조달 제품에서 잘못된 ‘참여 가능’ 판정은 일반적인 UI 오류보다 심각하다.

### 데이터 원칙

- 공고정보·정정공고·첨부파일의 수집시각을 기록한다.
- 판단 결과마다 공고 원문, 첨부파일 또는 공식 데이터 출처를 연결한다.
- 확정, 추정, 직접 확인 필요 세 상태를 사용한다.
- 조건을 해석하지 못하면 참여 가능으로 추정하지 않는다.
- 정정공고가 나오면 기존 분석을 만료시키고 재분석한다.
- 분석 모델·프롬프트·규칙 버전을 기록한다.
- 고객이 본 결과와 당시 근거를 감사로그로 보존한다.

### 출시 전 골든셋

실제 공고 최소 100건으로 검증셋을 만든다.

- 물품 30건 이상
- 일반용역 30건 이상
- IT·마케팅·교육·연구용역 30건 이상
- 정정공고, 공동수급, 지역제한, 실적요건 등 예외 공고 포함
- 전문가가 참가조건·필수서류·마감정보를 정답으로 검수

### 초기 목표치

다음은 출시 목표이며 실제 데이터로 갱신한다.

- 입찰 마감일 추출 정확도: 99.9% 이상
- 필수 참가조건 재현율: 98% 이상
- 근거가 연결된 판단 비율: 100%
- 유료 파일럿 중 중대한 허위 참여 가능 판정: 0건
- 정정공고 감지 및 재분석 성공률: 99% 이상

## 5. 사용자 경험 게이트

토스식 단순함은 기능을 숨기는 것이 아니라 사용자가 다음 행동을 고민하지 않게 하는 것이다.

- 한 화면의 핵심 행동은 하나만 둔다.
- 가입 전에 최소한의 진단 가치를 보여준다.
- 시스템이 알 수 있는 정보는 사용자에게 다시 묻지 않는다.
- 공식 용어는 쉬운 말로 설명하고 원문 용어를 함께 제공한다.
- 모든 버튼은 다음 화면에서 일어날 일을 설명한다.
- 홈은 기능 메뉴가 아니라 현재 상태와 오늘 할 일을 보여준다.
- 사용자가 막힌 이유와 해결 방법을 같은 화면에 제공한다.
- 제출 완료·결과 대기·낙찰·유찰 상태를 명확히 구분한다.
- 모바일에서도 공고 확인, 할 일 처리, 서류 확인이 가능해야 한다.

## 6. 보안·개인정보 게이트

- 운영환경 비밀정보는 저장소에 커밋하지 않는다.
- 전송구간과 저장 데이터 암호화를 적용한다.
- 회사별 데이터가 분리되는 권한 테스트를 둔다.
- 관리자 권한 사용을 감사로그에 남긴다.
- 업로드 파일의 확장자·크기·악성파일을 검사한다.
- 개인정보 수집 항목, 목적, 보관기간, 삭제 방법을 고지한다.
- 계정·회사 데이터 삭제 절차를 제공한다.
- 공동인증서 원본 또는 비밀번호를 서버에 저장하지 않는다.
- 결제정보는 인증된 결제대행사에 위임하고 카드정보를 직접 저장하지 않는다.
- 공개 저장소 샘플에는 실제 사업자·담당자 정보가 없어야 한다.

## 7. 운영 게이트

- 구조화된 오류로그와 요청 추적 ID
- 분석 실패율, API 지연, 정정공고 감지 실패 모니터링
- 결제·환불·권한 변경 감사로그
- 데이터베이스 백업과 복구 리허설
- 장애 공지와 고객지원 절차
- 오류가 난 분석을 운영자가 재실행할 수 있는 도구
- 고객에게 잘못된 결과가 노출됐을 때 영향범위를 찾는 기능
- 서비스 상태, 약관, 개인정보처리방침, 환불정책

## 8. 테스트 기준

### 자동 테스트

- 참가조건 규칙 단위 테스트
- 공공데이터·첨부파일 수집 통합 테스트
- 결제와 권한 통합 테스트
- 가입부터 제출 확인까지 E2E 테스트
- 정정공고 재분석 회귀 테스트
- 테넌트 간 데이터 격리 테스트
- 접근성·모바일 뷰포트 테스트
- 주요 페이지 성능 테스트

### 릴리스 전 수동 검증

- Chrome·Edge 최신 버전
- 모바일 360px 이상
- 느린 네트워크와 API 타임아웃
- 첨부파일 없음·손상·비표준 형식
- 공고 취소·정정·마감 경과
- 결제 실패·중복결제·환불
- 사용자가 중간에 나갔다가 돌아오는 흐름

## 9. 유료 베타 출시 게이트

다음 조건을 충족하기 전에는 ‘판매 가능한 버전’이라고 부르지 않는다.

- 실제 결제 고객 30개사 이상
- 실제 공고 50건 이상 처리
- 첫 입찰 완주율 70% 이상
- 환불률 5% 이하
- 공고당 사람 지원시간 중앙값 45분 이하
- 중대한 허위 참여 가능 판정 0건
- 근거 없는 자격 판단 0건
- 결제·환불·보안·백업·모니터링 운영 완료
- 고객지원 응답기준과 책임범위 고지 완료

## 10. Codex 작업 요청 형식

전체 서비스를 한 번에 만들어 달라고 요청하지 않는다. 아래 형식으로 하나의 완결된 세로 기능을 요청한다.

```text
작업명:
고객 상황:
완료해야 할 결과:
범위에 포함:
범위에서 제외:
공식 데이터 출처:
사용자 흐름:
수용 기준:
실패·예외 시나리오:
보안·개인정보 조건:
필수 자동 테스트:
운영·모니터링 조건:
릴리스 게이트:
```

좋은 작업 단위의 예시는 ‘공고 URL 입력부터 근거가 있는 참가조건 결과 저장까지’다. 나쁜 작업 단위는 ‘나라장터 SaaS 전체를 프로덕션급으로 만들어줘’다.
